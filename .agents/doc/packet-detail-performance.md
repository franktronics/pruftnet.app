# Stored packet detail performance

Date: 2026-09-05. Baseline: `a9936b5254800c4bdda6cf201a9646df7b0ca075`.

## Cause and implementation

The saved-capture detail handler previously called full segment recovery on every selection. It read all blocks, allocated a metadata vector for the segment, searched for the packet, and then reopened the file to read that packet. It repeated this for preceding segments as well. Bytes and dissection share the same binary response, so both panels waited for this work.

`capture/packet_index` now owns derived `.pcapng.pidx` sidecars. Each locator is a little endian packet ID and block offset (16 bytes). Runs of up to 4096 locators are sorted independently. Their headers contain ID bounds, record count, run number and corruption checksums. Lookup skips nonmatching runs, verifies matching runs, searches their locators and reads the selected packet directly after reading its section/interface headers. Out-of-order IDs from multiple interfaces and gaps in IDs are supported. Lookup examines one small header per run; it is not a globally sorted tree with logarithmic cost in total capture size. Memory stays bounded for unsegmented files too.

`pcapng_format` supplies one shared scanner for recovery, index reconstruction and direct reads. Sequential recovery no longer seeks back twice for each packet. Direct reads verify the selected block framing, lengths, capture identity, packet ID and interface metadata. A malformed second section is rejected without allowing recovery to truncate it as a partial tail. The spool format generated by Pruftnet has one section per segment.

## Capture and resource isolation

The analyzer forwards already committed metadata to a dedicated index thread in batches of at most 4096 records. The capture callback and raw writer do no index I/O. The queue holds at most two batches; the producer and consumer each hold at most one additional batch. The short queue mutex never covers filesystem work. There is no wait for queue capacity. If it is exhausted, the producer abandons the rest of that segment's index. A later detail read reconstructs it. Skipped batches cannot result in publication of a partial index. The index thread is joined during analysis finalization, so outstanding index work can add a small finalization delay.

This adds approximately 16 bytes of disk writes per packet, plus 48 bytes per run and a 64-byte file header. Sidecar bytes are derived storage outside the existing raw spool quota, like other derived capture data. Index errors never fail capture or prevent a valid raw packet from being returned. Under sustained disk or CPU saturation the sidecar may be absent, preserving capture/analysis priority rather than guaranteeing an index for every segment.

An index is published from a unique temporary directory only after all packet blocks in the segment are committed and the source size matches the last indexed block. Publication uses rename. Readers verify the format version, capture identity, source size and modification time, file length and relevant checksums. Invalid locators or stale/corrupt indexes fall back to reconstruction. The raw block remains authoritative; these checksums detect accidental damage, not malicious changes with recomputed checksums. A source changed during a read is rejected. Ring eviction and temporary capture cleanup remove sidecars; publication also checks for eviction racing the rename.

Missing indexes on older captures are reconstructed lazily on the native detail thread, one segment at a time, with bounded memory and cooperative cancellation. This is not an eager migration at application startup: the first lookup can still require a scan of preceding unindexed segments and the selected segment. Subsequent selections and process restarts reuse published indexes. An interrupted build is removed. A hard process crash can leave an ignored temporary directory, which is removed with the capture directory. No raw capture data or schema migration is required.

## Cancellation

HTTP detail requests now listen to response closure as well as aborted input, including cancellation after a complete GET has already arrived. Effect interruption and timeout send a one-way native cancellation notification only when the worker advertises `detailCancellation` in its handshake. Older workers remain usable and drain late responses without receiving unsupported notifications.

Native cancellation is keyed by transport request ID. Queued requests are removed and receive exactly one cancelled response; active scans check a stop token between blocks and index runs. Cancellation never kills the shared worker or cancels another request. A dissection or artifact write already in progress completes normally; unclaimed artifacts are still cleaned up. Shutdown cancels outstanding details before draining the queue. No artificial debounce, aggressive prefetch, frontend change or unbounded cache was introduced.

## Measurements

Local macOS, existing 213,741-packet / 252,463,940-byte spool segment copied into a temporary directory. Original files were not modified. These are storage-only measurements with the local non-Release CMake build, not HTTP-to-display latency. Cache state was not forcibly reset.

| Case | Result |
| --- | --- |
| Previous full scan to the last packet, median of 5 | 2100.73 ms |
| First legacy reconstruction, one observation | 2240.04 ms |
| Indexed first packet, median of 20 | 1.06 ms |
| Indexed middle packet, median of 20 | 1.08 ms |
| Indexed last packet, median of 20 | 0.38 ms |
| Synchronous index emission from committed metadata, median of 5 | 72.71 ms total |
| Persistent index size | 3,422,464 bytes, about 1.36% of raw size |

A separate 50,000-packet synthetic runtime burst was run seven times per version, with enough ring capacity to retain the burst. Median completion was 981.87 ms for the baseline and 981.92 ms with the dedicated index thread. Every run persisted and analyzed all 50,000 packets; every updated run also published its index. This test includes runtime startup and finalization and is not a hardware capture throughput ceiling. It found no material regression in this workload, but cannot establish zero overhead on every machine or under sustained load.

Sources and raw results are in [packet-detail-performance/](packet-detail-performance/). To reproduce on macOS/Linux after building C++:

```sh
python3 .agents/doc/packet-detail-performance/run-probes.py /absolute/path/to/capture.pcapng
```

The script extracts the old recovery/runtime sources into a temporary directory for comparison. All other native components use the current library. The historical enum switch emits a harmless warning about the new cancellation enum; this branch is never used in the baseline probe.

## Validation and limits

- Native: 43 CTest cases passed; two hardware live-interface cases skipped.
- Core: 61 Vitest tests passed, including legacy-worker handshake compatibility.
- Tests cover persisted/rebuilt binary detail equality, out-of-order and gapped IDs, multiple interfaces and timestamp resolutions, bounded background production, absent/truncated/corrupt/stale indexes, unavailable index destinations, wrong capture identity, corrupt raw blocks, cancellation during scanning, temporary-file cleanup, and active/queued cancellation through the real native worker with another request surviving.
- Core type checking and lint passed. Server and desktop main builds passed; desktop retained its pre-existing URL-resolution build warnings.
- Linux and Windows runtime behavior and actual frontend presentation latency were not measured on this macOS host. The implementation uses portable C++20, shared Node code and explicit Windows rename handling. No new platform dependency was added.
